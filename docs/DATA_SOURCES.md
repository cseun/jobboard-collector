# 로봇 채용 보드 — 데이터 수집·공유·비용 정리

> 작성일: 2026-11-24 · 대상: 직접 운영 중인 채용 보드(Oracle Cloud VM, FastAPI + PostgreSQL + Docker + Caddy)
> 이 문서는 "지금 어떤 데이터가 있고, 어디서 어떻게 모았고, 어떻게 공유하고, 비용을 어떻게 줄였는지"를 기록한 것입니다.
> ✅ 직접 확인 / 🟡 기록·파일 기준으로 추정 / ❓ 확인 못 함

## 0. 이용 목적과 범위

이 보드는 **운영자 본인의 취업 준비를 위한 개인용 사이트**입니다.

| 항목 | 내용 |
|---|---|
| 목적 | 본인의 구직 활동(공고 확인, 지원 관리, 면접 준비)에만 사용 |
| 수익 | 금전적 이득을 얻지 않음. 유료 서비스·광고·판매·유료 배포를 하지 않음 |
| 접근 | 초대 코드를 받은 사람만 로그인할 수 있고, 외부에 공개하지 않음(현재 SSH 터널 접속) |
| 원문 | 공고는 원문 URL로 연결하고 출처(사이트명)를 함께 표시. 원문 사이트를 대체하려는 목적이 아님 |
| 서버의 수집 | 현재는 채용 사이트를 자동으로 읽지 않음(3장). 보강기를 만든 뒤에는 로그인 없이 보이는 공개 페이지만 천천히, 하루 상한을 두고 읽음 |
| 로그인 정보 | 채용 사이트의 비밀번호·로그인 세션을 서버에 저장하지 않음 |
| 로그인해야 보이는 내용 | 다른 사용자에게 공유하지 않고 본인 계정에서만 보도록 정리 중(7장) |
| 로그인 화면 | 같은 취지의 이용 안내를 로그인 화면에도 표시 |

> 이 표는 **현재 운영 방침을 적은 것**입니다. 판매·배포·공개 서비스로 바뀌면 이 장과 3·5·7장을 먼저 고쳐야 합니다.

### 1-5. 이 표에서 정해진 것
- 🌐 **로그인 없이 읽히는 공개 정보**는 서버가 새벽에 천천히 읽는다. 공공데이터·공시는 공식 API로 받는다.
- 🔐 **로그인이 필요한 정보**는 서버에서 수집하지 않고, 내가 직접 보고 입력한다.
- 🖼️ **이미지 공고**는 공고 상세 보강 때 함께 AI로 읽는다(누른 공고만 읽는 방식이 아님).
- 🤖 AI가 필요한 건 "이미지 글자 읽기"와 "여러 개를 묶어 판단하거나 요약하는 일"뿐이고, 값을 읽어 오는 일은 AI 없이 한다.

## 3. 공고를 어떻게 수집했나

| 단계 | 방식 | 도구 |
|---|---|---|
| 수집 | Claude 일일 예약 작업이 웹에서 공고를 찾아 읽고 구글 시트와 마스터 파일에 누적 | Claude 예약 작업 (2026-11-15부터 중지) |
| 보관 | 시트: `채용공고`(보드 형식), `추가수집_사람인`, `추가수집_잡코리아·원티드` 3개 탭 | Google Sheets |
| 서버 반영 | 시트를 탭마다 CSV로 받아 서버에서 실행. 미리보기 후 `--apply` | `scripts/sync_sheet.py` |

`sync_sheet` 동작 규칙
- 새 공고는 추가하고(`[신규·시트]` 표시, 출처 '시트'), 이미 있는 공고는 **접수 상태·마감·최종 확인만 갱신**하고 빈 칸만 채워요. 설명·필수·우대는 덮어쓰지 않아요.
- URL이 없는 행은 회사명+공고명으로 맞춰요. 같은 이름인데 URL이 다르면 건너뛰고 보고해요.
- 지원 상태·적합도·적합 이유·확인 내용은 가져오지 않아요(내가 직접 정리한 값이 아니라서).
- 같은 파일을 다시 돌려도 결과가 같아요(멱등).

## 6. 비용을 줄이려고 한 것

| 방법 | 효과 |
|---|---|
| 시트 반영(`sync_sheet`)은 **AI 토큰 0** | 매일 돌려도 AI 비용이 없음 |
| AI 기능은 **사용자가 등록한 자기 키**로만 동작(키는 암호화 저장, 끝 4자리만 표시) | 서버 운영자가 AI 비용을 떠안지 않음 |
| 계정별·날짜별 AI 호출 수와 토큰 수를 기록 | 사용량 확인과 제한이 가능 |
| 이미 있는 공고는 접수 상태·마감·확인일만 갱신 | 불필요한 재수집·재처리를 줄임 |
| 미리보기 후 `--apply` | 잘못된 파일로 DB를 오염시킨 뒤 되돌리는 비용을 줄임 |
| 정적 파일은 Caddy가 그대로 제공 | 화면 변경 시 서버 재시작 없이 파일 교체만 하면 됨 |
| 국내 공고 목록에 **페이징** | 1,580건 화면 렌더링 약 1,100ms → 약 30~55ms |
| 공개 페이지와 공공데이터를 우선 | 로그인 세션 관리·차단 대응 같은 유지 비용을 피함 |

계획 중인 절감책
- 이미지 공고는 **공고 상세 보강 때 함께 AI로 읽는다.** 비용이 커지지 않도록 아래 제한을 둔다(제안).
  - 하루에 읽을 이미지 공고 수에 상한을 둔다.
  - 한 번 읽은 결과는 저장해 같은 공고를 다시 읽지 않는다.
  - 마감이 지난 공고, 이미 칸이 채워진 공고는 건너뛴다.
- 공고 상세 보강은 새벽에 천천히, 하루 상한을 두고 빈 칸이 있는 공고만 대상으로 한다.
- 이 AI 호출에는 **관리자 계정에 등록한 키 하나**를 쓴다(결정 2026-11-24). 서버의 AI 호출 코드는 Claude·ChatGPT·Gemini 세 서비스의 이미지 입력을 모두 지원한다. 어느 서비스·모델로 할지는 읽혀 보고 비교해서 정한다 → **비교 기록은 9장**(권장: Claude Sonnet 5.5 기본 설정).

## 7. 결정된 방향 (2026-11-24)

**정보를 두 종류로 나눈다.**

- 시트는 공개 정보를 올릴 때의 중간 저장소로 쓰고, 서버가 매일 자동 반영(cron)한다(링크 공유 방식).

### 9-1. 테스트 방법
| 항목 | 내용 |

### 9-4. 알게 된 것
1. **구조(칸) 문제는 프롬프트 설계 문제였다.** 1차 프롬프트에는 `필요역량` 칸이 없어서 Sonnet이 그 구역을 통째로 버렸고, Haiku는 그걸 필수에 합쳐 넣었다. 칸을 늘리고 "구역을 따르고, 안 맞는 글은 기타안내에 보존"으로 바꾸자 두 모델 모두 필수 5·우대 7·필요역량 2로 맞았다. **보강기는 고정 칸에 안 맞는 내용을 버리지 않고 `기타`로 모은다.**
2. **Haiku는 사고를 꺼도 켜도 "사내"를 "새내"로 읽는다**(5회 연속). 필수·우대 판단에는 영향이 없는 글자 오타지만 보드에 그대로 보인다. Sonnet은 이 글자를 틀리지 않았다.
3. **Haiku는 사고를 끄면 더 나빠진다**(항목 누락과 오독이 늘어남). 비용 절약은 $0.0017 → $0.0009로 작아서 얻는 게 없다.
4. Haiku는 같은 이미지를 읽을 때마다 결과가 달라졌다(1차 프롬프트에서 4회 중 2회 필수가 7개). Sonnet은 2회 모두 거의 같았다.
5. **Sonnet은 effort를 낮춰도 출력이 1,051 → 1,037토큰으로 거의 같다**(원래 생각을 많이 하지 않음). 낮춰서 얻는 절약이 없으므로 기본값으로 둔다.
6. Haiku 5.5는 기본으로 적응형 사고가 켜져 있어서 출력의 상당 부분이 겉으로 안 보이는 사고였다(보이는 JSON 약 700토큰인데 출력은 2,176토큰). 사고를 끄는 건 effort가 high 이하일 때만 가능하다. Sonnet 5.5는 사고를 끌 수 없고 `effort`로만 조절한다. 문서에는 Haiku 5.5가 사고를 끄거나 effort를 낮추면 답에 추론 같은 글을 섞는 일이 늘 수 있다고 되어 있다.
7. 2차 프롬프트에서 Sonnet의 출력이 1,051 → 2,690토큰으로 늘어 비용이 약 2배(건당 약 48원)가 됐다. 하단의 법정 고지문(채용서류 반환 청구 등)까지 `기타안내`에 옮겨 적었기 때문이다. 보강기에서는 법정 고지문은 건너뛰도록 줄일 예정이다(절감 효과는 아직 실측 전).

### 9-7. 정정 기록
- 처음에 Haiku가 필수 2개를 "지어냈다"고 판단했으나 **오판**이었다. 그 문장은 원본의 "필요역량" 구역에 실제로 있었고, Haiku는 구역을 필수에 합쳤을 뿐이다. 오히려 Sonnet이 그 구역을 누락했고, 원인은 프롬프트에 칸이 없었던 것이다.
- 하루 20건 상한이 "월 500원 수준"이라고 한 계산은 **틀렸다**. 상한에 매일 꽉 차는 최악의 경우 월 수 달러~십수 달러가 된다(위 9-5).

### 9-8. 권장안 (확정 대기)
- **이미지 공고 읽기는 Claude Sonnet 5.5 기본 설정**으로 한다. 이유: 글자 오독이 없고 결과가 일정하며, Haiku와의 월 차이는 약 1,800원이다. 보드에 원본 링크를 남겨 확인 경로를 둔다.
- Haiku 5.5는 이미지가 아닌 단순 작업(분류·요약 등)에 쓴다.
- 프롬프트는 2차(구역 제목 따르기 + 기타안내 보존 + 추측 금지)를 쓰고, 법정 고지문은 건너뛰게 줄인다.
- 하루 이미지 읽기 상한은 10건, 새벽 실행, 마감·충원·이미 읽은 공고는 건너뛴다.
- 남은 확인: 다른 회사 이미지 공고 2~3건으로 같은 기준 재확인, "경조금/경상조금" 원본 대조.

### 9-9. Haiku 2단계(읽기 + 이상한 단어 교정) — 시험 결과: 이 용도로는 비추천
| 항목 | 내용 |
|---|---|
| 방식 | 1단계 Haiku가 이미지를 읽고, 2단계 Haiku가 **글자만 받아** 오타로 보이는 단어를 찾는다(이미지를 다시 보내지 않음). 정정 목록(`원문 → 수정, 이유`)만 받아 저장된 글자에 바꿔 넣고, 확신이 없는 단어는 `의심`으로만 표시한다 |
| 기대(시험 전) | "새내근로 복지기금 → 사내근로복지기금"처럼 **말이 안 되는 단어**는 언어 지식으로 고칠 수 있고, 2단계 비용은 건당 약 $0.0003일 것으로 예상했다 |
| 한계 | ① 항목 누락·구역 합침 같은 **구조 오류는 못 고친다**(글자만 보기 때문). ② 이미지를 다시 안 보므로 "경조금/경상조금"처럼 **둘 다 말이 되는 단어**는 판단할 수 없다. ③ 맞는 단어를 잘못 고칠 위험이 있어 "확실한 것만 정정, 나머지는 의심" 규칙이 필요하다 |
| 무료 보완책 | Haiku가 반복해서 틀리는 단어는 **고정 교정표**(예: 새내근로 → 사내근로)로 AI 없이 바꾼다. 토큰 0원 |
| 도구 | `--proofread` 옵션(`docker compose exec -T api python -m scripts.test_image_read --provider anthropic --model claude-haiku-5-5 --proofread 이미지주소`), 교정 모델은 `--proof-model`로 따로 지정 가능 |

**시험 결과 (2026-11-25, 이미지 1건, Haiku 1단계 + Haiku 2단계)**
| 2단계가 한 일 | 판정 |
|---|---|
| "사회직무 교육지원 → 사외직무 교육지원" | ✅ 맞음(Sonnet이 읽은 값과 일치) |
| "우리사주 취득기금 → 우리사주 취득자금" | ❌ **맞는 단어를 틀리게 고침.** 1단계와 Sonnet 모두 "취득기금"으로 읽었고, 2단계가 "표준 표현"이라는 근거로 바꿨다. 근거가 그럴듯해서 눈치채기 어려운 유형 |
| "새내근로 복지기금" | ❌ 못 고침. "본문 다른 곳('새내 기준')에도 같은 표현이 있어 원문일 수도 있다"며 **의심만 함.** 같은 오독이 여러 곳에 반복되면 오히려 원문처럼 보임 |
| "새내 기준"(기타안내) | ❌ 못 고침 |
| 의심만 한 것: "경조휴가 경상조금", "해외여행에 결격사유", "Digital & Analog…(1년 ~ 4년)" | 뒤의 둘은 원문이 맞음(스크린샷으로 확인) → 불필요한 의심. "경상조금"은 아직 미확정 |

| 비용·시간 | 값 |
|---|---|
| 2단계 입력 / 출력 | 1,731 / **2,148 토큰**(고친 목록은 짧은데 출력이 큼 → 겉으로 안 보이는 사고 토큰) |
| 합계 비용 | 약 $0.0034(약 4.8원), 시간 약 22초 |

**결론**
1. 정정 2건 중 1건만 맞고, 핵심 오독 2건(새내근로·새내 기준)은 남았으며, **원래 맞던 값을 틀리게 만든 정정이 1건 생겼다.** Sonnet(오독 0건)을 대체하기엔 부족하다.
2. 글자만 보는 교정은 "말이 안 되는 단어"는 잡아도, **같은 오독이 반복되면 못 잡고, 그럴듯하게 틀리게 고칠 수 있다.** 원본 이미지를 다시 보지 않는 한 한계가 분명하다.
3. 2단계 출력 토큰이 커서 예상(건당 $0.0003)보다 4배 비쌌다. 그래도 Sonnet의 약 10분의 1이다.
4. 대안: (a) Sonnet 1단계(권장), (b) Haiku 1단계 + **고정 교정표**(새내근로→사내근로, 새내 기준→사내 기준, 사회직무→사외직무: AI 없이 0원, 이미 아는 오독만 처리), (c) 교정 결과를 **자동 적용하지 않고 "의심 표시"만** 붙여 사람이 확인.

**제목 AI 판정** (`scripts/title_judge.py`, 저장 모드 기본 켜짐 · 끄기 `--no-judge` · 미리보기에서 써 보기 `--judge`)
- 새 공고를 **제목·회사 이름으로** 가벼운 모델(`claude-haiku-5-5`, `--judge-model`)에게 ○ 관련 / △ 애매 / × 관련 없음 으로 묻고, **×만 저장하지 않음**(60건씩 묶어 한 번에 질문, 한 번에 최대 4,000건 `--judge-max`). 단가 입력 $0.10 · 출력 $0.50 / 100만 토큰 기준 3,000건이 몇 센트 수준.
- 애매하면 △(남김). 모델이 실패하거나 JSON이 아니면 그 묶음은 전부 △로 남김 — 판정 때문에 공고를 잃지 않게. ○·△는 공고의 `관련도` 칸에 기록(보드에서 △만 따로 볼 때 씀).
- ×로 거른 공고는 `collector/titleDrop` 문서에 기억(최대 2만 건) → 다음 날 '아는 공고'로 세서 **다시 묻지 않고**, 연속 5건 멈춤 기준도 그대로 작동.
- 미리보기 출력 `AI 제목 판정`: ○△× 건수 · × 예시 15건 · △ 예시 10건 · 토큰·비용. 저장 모드는 실행 기록(`--report`)에 비용이 합산됨.
- **확정한 제외 기준(2026-11-25)**: ① 요구 경력(최소)이 **5년 초과**면 저장 안 함(5년까지는 수집, `--max-career`, `MAX_CAREER=5`) ② 기술영업 ③ 기획자·PM ④ 팀장·리드·책임·수석급(단, 책임급과 팀원을 같이 뽑는 공고는 아래 '직급 확인'으로 상세를 보고 결정) ⑤ 일반 웹/앱 서비스 개발. 단어로 확실한 것(본부장·센터장·실장·임원·기획자·프로덕트/프로젝트 매니저·영업)은 `exclude_words.txt`가 먼저 막고, 나머지(웹/앱·애매한 PM)는 AI가 맥락으로 판정. MES·스마트팩토리·로봇 관제·장비 제어 UI·AI 서비스를 만드는 웹/앱은 남김.
- **직급 확인(2026-11-25 결정)**: 팀장·책임·수석·리더·Lead·총괄이 제목에 있으면(`scripts/senior_words.txt`) 바로 버리지 않고 **상세 본문을 읽어 팀원·사원급도 뽑는지** Haiku가 확인. 팀원도 뽑으면 저장(`직급 확인`="상세 확인: 팀원급도 채용"), 책임급만 뽑으면 저장하지 않고 기억. 상세를 못 읽으면(잡코리아·원티드·이미지 공고) 저장하되 `관련도` △ + `직급 확인`="상세 미확인". 본부장·센터장·실장·임원은 단어로 바로 제외(`exclude_words.txt`).

- **판정 기준 보정(2026-11-25 오후)**: 첫 전체 판정에서 모델이 '직무는 맞는데 로봇·제조 맥락이 안 보인다'는 이유만으로 ×를 준 사례(의료 AI 서비스 엔지니어, LLM·VLM 튜닝, QA/QC, 머신비전 광학기구, MES·AX PM)가 나와 기준을 고침: ① 산업·맥락이 낯선 것은 ×의 이유가 아니라 △의 이유 ② SW QA·QC·테스트는 도메인 무관 최소 △ ③ 비전·로봇·AMR·자동화 분야의 광학·기구·HW 설계는 △(일반 기구설계만 ×) ④ MES·AX·스마트팩토리·로봇·Physical AI 분야 PM·컨설턴트는 △(순수 PM만 ×) ⑤ LLM·에이전트·RAG·생성형 AI·AX는 도메인 무관 ○(일반 ML 모델 개발만 ×).
- **보드 반영**: `관련도`가 ×인 공고는 보드에서 자동으로 숨김(`tools/patch_irrelevant.mjs`) — 기존 "🚫 숨긴 공고" 보기에 모임, 지우지 않으니 되돌릴 수 있음. 완전히 지우려면 `scripts.cleanup_excluded --x [--career 5]`(미리보기 → `--apply`).
- **모델 비교 시험**(`scripts/judge_compare.py`): 내장 시험 세트 45건(`judge_samples.tsv`, 정답은 Claude 기준이라 고쳐 쓰기)으로 Haiku·Sonnet·Jev를 같은 공고에 돌려 정답 일치·×를 놓친 수·좋은 공고를 ×로 보낸 수·비용·시간을 비교. Jev(`api.typesafe.ai/v1/systemone`, 모델 `jev-latest`, 입력 $0.042/100만 토큰·출력 무료)는 TYPESAFE_API_KEY가 있어야 함. Jev는 이유 글 없이 확신도만 줌.
- 판정 기준(프롬프트)은 `title_judge.PROFILE`: ○ 로봇 SW·임베디드·PLC·장비제어·비전·QA·AI/LLM/AX·MES/스마트팩토리·필드/기술지원 · × 디자인·기획·마케팅·영업·경영지원·생산/조립·기구/기계/전기 설계·교육/강사·일반 머신러닝 엔지니어 · △ 직무 불분명·일반 웹/앱 개발.

**이미 저장된 공고 판정** (`scripts/judge_existing.py`): 보드에 있는 공고를 같은 기준으로 ○/△/× 판정해 `관련도` 칸에 적음. **지우지 않음**(미리보기 → `--apply`로 기록). × 목록을 보고 맞으면 정리, 틀리면 `title_judge.PROFILE`을 고침 — 판정 기준이 좋은 공고를 ×로 보내지 않는지 시트 공고(약 1,500건)로 먼저 검증하는 데에도 씀.
**머신러닝 엔지니어**는 제외어가 아니라 AI 판정이 맥락으로 처리: 로봇·Physical AI·제조·임베디드·비전 맥락이면 ○/△, 추천·예측·커머스 같은 서비스 ML이면 ×. (단어로 막으면 "로봇 머신러닝 엔지니어(Physical AI)" 같은 좋은 공고가 같이 빠져서 제외어에서 뺌)

**원티드**는 서버 IP를 막아서(403) 서버 수집에서 빼고(`COLLECT_SOURCE` 기본 `saramin,jobkorea`) **내 PC Chrome 예약**으로 받음 → `docs/LOCAL_WANTED_COLLECTION.md` (`/api/admin/job-plan` · `/api/admin/job-import`).

**이미 저장된 공고 정리** (`scripts/cleanup_excluded.py`): 제외 단어에 걸리는 옛 공고를 정리. 기본 미리보기 → `--apply`. 제목·회사만 봄 · 기본은 수집기 공고(`[신규·수집]`)만(`--all`이면 시트 공고도) · 내 개인 데이터에 공고 주소/번호가 들어 있으면 지우지 않음 · 지우기 전 `pg_dump` 백업 권장. 단어는 복합어로(예: `생산직`, `오퍼레이터`). `교육`·`생산` 단독은 좋은 공고(교육용 로봇 SW, 생산관리·MES)가 같이 빠져서 넣지 않음.

**수집이 멈추는 기준과 놓칠 수 있는 경우** (`scripts/collect.py` `STOP_KNOWN=5`, 옵션 `--stop-known`)
- 멈춤 조건: 한 키워드에서 "이미 아는 공고 / 다른 키워드와 겹친 공고 / 조건으로 건너뛴 공고"가 **연달아 5건**. 새 공고가 하나라도 나오면 연속 카운트가 0으로 돌아감.
- 정렬은 관련순이 아니라 **등록일순**으로 요청함(사람인 `recruitSort=reg_dt`, 잡코리아 `Ord=RegDtDesc`, 원티드 `job_sort=job.latest_order`).
- 그래도 놓칠 수 있는 경우(실제 사이트 정렬은 아직 검증 못 함):

| 위험 | 설명 |
|---|---|
| 상단 광고/고정 공고 | 날짜순이어도 맨 위에 광고가 섞이면, 아는 공고가 연속 5건 이상일 때 1쪽에서 멈춤 |
| 필터로 건너뛴 공고 | 경력 초과·제외어 공고도 "아는 공고"로 세므로 연속 5건이면 뒤의 새 공고를 못 봄 |
| 끌올/수정 공고 | 옛 공고가 다시 올라오면 위쪽에 아는 공고가 끼어듦 |

- **검증법**: 서버에서 미리보기를 두 번 돌려 비교. `collect --source all` 과 `collect --source all --stop-known 30` 의 새 공고 수가 같으면 정렬을 믿어도 됨. 30 쪽이 더 많으면 아래 보완 중 하나 적용.
- **보완 후보**: ① 연속 기준을 10~15로 올림(단순, 요청 약간 증가) ② 필터로 건너뛴 공고는 연속 카운트에서 제외(정확, 코드 수정 필요) ③ 주 1회 `--stop-known 999` 전체 훑기(회수 가능, 차단 위험 증가 — 마지막 수단).
- 상태: 위 검증은 아직 서버에서 안 돌려 봄. 결과에 따라 이 항목을 갱신할 것.

**미리보기가 알려주는 것**: 키워드별 읽은 쪽·목록 건수·새 공고·아는 공고·겹침·멈춘 이유, 중복 뺀 새 공고 수, 등록일 분포, 상세 요청 예정 수. 이 숫자로 하루 요청 수와 새 공고 수(예상 30~45건)를 먼저 확인한 뒤 `--apply`.

**알려진 한계**
- 사이트는 사람인·잡코리아·원티드 3곳(`--source saramin|jobkorea|wanted|all`, 쉼표로 여러 개). 아래 10-4-1 표 참고.
- 텍스트 공고의 `필수`·`우대`는 아직 칸별로 나누지 않고 본문만 `원문 본문`에 저장(규칙 파서 또는 AI는 다음 단계). 이미지 공고는 AI가 칸별로 채움.
- 이 샌드박스에서는 사람인에 접속할 수 없어, 화면 구조(`.item_recruit`·`.job_day` 등)는 브라우저로 실제 페이지를 보고 맞췄고 **시험은 그 구조를 옮긴 예시 파일(`tests/fixtures`)로 함**. 실제 서버에서의 첫 `--dry-run` 결과를 꼭 확인하세요. 사이트 구조가 바뀌면 `parse_list`·`parse_detail`만 고치면 됩니다.
- AI는 계정에 등록된 Claude 키를 씀(`--email`로 계정 지정, 없으면 첫 관리자). 키가 없으면 AI 단계만 건너뛰고 나머지는 저장됩니다.
- 자동 실행은 10-6의 cron으로 켭니다. 미리보기·1~2회 수동 저장으로 결과를 본 뒤 켜는 것을 권장.

### 10-6-2. 빈칸 채우기 구조 (2026-11-25 확정: DB가 원본, 시트는 입력 전용)
```
서버 수집기(사람인) ─▶ DB ◀─ 서버 보강(이미지=Sonnet AI · 텍스트=규칙 파서)
                         │
       GET /api/admin/gaps (빈칸 목록) ─▶ 내 PC가 찾아봄 ─▶ POST /api/admin/jobs/{id}/fill ─▶ DB
시트(손으로 적은 공고) ─▶ sync_sheet ─▶ DB   (입력 방향만. DB → 시트 내보내기는 안 함)
```
- **빈칸**: 값이 없거나 `원문 확인 필요`·`미확인` 같은 자리표시 글자인 칸. 점검 대상: `필수`·`우대`·`급여(공고)`·`전형 절차`·`근무 위치`·`등록일`(`우대`의 `—`는 '없음'이라 빈칸 아님). 마감된 공고는 기본 제외.
- **조회** `GET /api/admin/gaps?fields=필수,우대&limit=50` (관리자 로그인): 칸별 빈 공고 수(`summary`)와 공고 목록(제목·URL·원문 본문·이미지 주소·이미 있는 값)을 줍니다.
- **채우기** `POST /api/admin/jobs/{id}/fill` `{"fields": {...}, "by": "내PC"}`: **기본은 빈칸만** 채우고 값이 있으면 건너뜀(이유를 알려 줌). 덮어쓰려면 `"overwrite": true`. 허용 칸만 받고(기업명 등은 거부), 날짜는 형식·미래 여부 검사, 4,000자 제한. 채운 곳·날짜는 `채움 기록`에 남음.
- **내 PC 도우미** `tools/fill_gaps_client.py`: 로그인 → `list` → (찾아서 `fills.json` 작성) → `fill`. 서버에는 SSH 터널(`http://localhost:18080`)로 접속하고 비밀번호는 입력창이나 환경변수로만 받음. 별도 토큰은 만들지 않았습니다(기존 관리자 로그인 재사용).
- **(2026-11-25 갱신) 서버가 직접 채우는 방식을 추가했습니다**: `scripts/fill_gaps.py`가 매일 수집 뒤 빈칸 공고를 규칙 파서 → AI 순서로 채웁니다. 최종 정리는 `docs/UPDATE_GUIDE.md`. 아래 PC 방식은 특정 공고를 직접 고칠 때만 씁니다.
- 이 방식이라 **PC가 꺼져 있어도 수집·AI 읽기는 계속 돌고**, PC는 서버가 못 채운 칸만 가끔 채웁니다. 구글 시트는 지금처럼 손으로/PC 루틴이 적는 입력 통로로만 쓰고, 시트 자동 반영(cron)은 만들지 않았습니다(필요하면 `sync_sheet`를 cron에 걸면 됨).

### 10-6-3. 텍스트 공고 필수·우대 (규칙 파서)
`--details`로 새 공고를 열 때 본문에서 `자격요건·필수·지원자격`과 `우대사항·우대조건` 구역을 찾아 `필수`·`우대` 칸에 넣습니다(`scripts/text_requirements.py`, AI 비용 0, `필수·우대 출처`=규칙 파서).
- 구역 제목은 짧아야 하고(25자 이하) 같은 줄에 붙은 내용(`필수: …`)도 읽음. 항목 앞의 점·번호는 지움. 한 구역 최대 1,500자.
- `주요업무 / 자격요건`처럼 업무와 자격이 한 제목에 섞인 구역은 **나누지 않고 비워 둠** → 빈칸 목록에 올라와 나중에 채움. 못 찾으면 `원문 확인 필요`로 남음.
- 정확도는 규칙의 한계가 있어 틀린 구역을 가져올 수 있으니, 처음 며칠은 보드에서 샘플을 확인하세요.

### 11-2. 기억해 둘 것 (실수하기 쉬운 곳)
- **`cleanup_excluded`는 기본이 '수집기가 가져온 공고(구분=[신규·수집])'만 대상** — 서버의 1,582건 대부분은 구글 시트에서 옮겨 온 것이라 지우려면 `--all`이 필요. `--full`을 붙이면 지울 공고 전체를 주소와 함께 출력(구글 시트에서 같은 행을 지울 때 사용). DB에서만 지우고 시트에 남기면 다음 `sync_sheet`에서 되살아나므로 시트도 같이 정리.
- `judge_existing`은 **이미 관련도가 있는 공고는 건너뜀**. 기준을 바꾼 뒤에는 반드시 `--redo`를 붙여야 새 기준이 적용됨.
- `cleanup_excluded --x`는 DB에 저장된 `관련도` 태그를 보고 지움 → **먼저 `judge_existing --apply`(태그만 저장, 삭제 아님)**.
- 태그만 저장해도 보드에서 ×는 자동으로 숨겨짐(되돌릴 수 있음). 삭제는 그 뒤 따로.
- 제목이 길게 요약된 시트 유래 공고는 모델이 본문 속 단어로 도메인을 추측해 오판하기 쉬움 → 기준에 "도메인은 ×의 이유가 아니다" 명시.
- 판정 기준을 바꾸면 `judge_samples.tsv`(정답 48건+)에 사례를 추가해 두면 모델 비교에서 바로 확인 가능.

**검토한 대안(구현 안 함)**
| 안 | 요지 | 판단 |
|---|---|---|
| A. 한 번에(현재) | 전체 맥락 유지, 호출 1번 | 채택 |
| B. 조각별 호출 | 호출당 일이 작지만 경계 맥락이 끊김 | 필수/우대 구분 때문에 보류 |
| C. 2단계 | 조각별로 글자만 옮겨 적고 → 텍스트로 구조화 | 비는 칸이 많으면 시도 |
| D. 이웃 조각 포함 | 조각 N을 읽을 때 N−1을 같이 보냄(RAG식) | 이미지 입력 약 2배 |
| E. 겹침 확대 + 구역 제목 전달 | D보다 싸게 같은 효과 | 후보 |

**다음 검증**: 첫 실행에서 `필수`·`우대`가 비는 비율, JSON 실패율, `truncated`, 실제 `cost_usd`를 확인하고, 문제가 있으면 같은 공고 5~10건으로 A·D·E를 비교한다.

### 11-11. 이미지 읽기 비교 시험(예측 vs 실제) — `scripts/image_compare.py`

같은 이미지 공고를 여러 방식으로 읽어 **① 비용 예측이 맞았는지 ② 읽은 내용이 어떻게 달라지는지 ③ OCR을 쓰면 비용·성능이 어떻게 되는지**를 기록한다. DB는 건드리지 않는다. 대상은 이미 Sonnet으로 읽어 둔 이미지 공고(무작위 N건, `--seed`로 고정).

**시험 항목(총 15개 설정, 기준선 S)**

| 묶음 | 설정 | 모델 | think | effort | 조각/겹침 | 알고 싶은 것 |
|---|---|---|---|---|---|---|
| 기준선 | S | Sonnet 5.5 | 켬(끌 수 없음) | 기본 | 900/40 | 예전 방식 |
| ① think·effort | H1 | Haiku | 끔 | 기본 | 600/150 | 현재 운영 설정 |
| | H2 / H3 | Haiku | 끔 | low / high | 600/150 | effort 영향 |
| | H4 | Haiku | 켬 | 기본 | 600/150 | think 영향 |
| | H5 / H6 | Haiku | 켬 | low / high | 600/150 | think×effort |
| ② 조각·겹침 | H0 | Haiku | 끔 | 기본 | 900/40 | 예전 조각 + Haiku |
| | G1 | Haiku | 끔 | 기본 | 900/150 | 겹침만 늘림 |
| | G2 | Haiku | 끔 | 기본 | 600/40 | 조각만 잘게 |
| | G3 / G4 | Haiku | 끔 | 기본 | 400/40, 400/150 | 더 잘게 |
| | G5 | Haiku | 끔 | 기본 | 600/0 | 겹침 없음(겹침 효과 분리) |
| ③ OCR | T | (AI 없음) | - | - | 2000/100 | Tesseract만 — 글자는 얼마나 읽나 |
| | TA | Haiku(글자만 받음) | 끔 | 기본 | 2000/100 | Tesseract 글자 → AI가 칸 나누기, 이미지는 안 보냄 |

- think 켬 = thinking 설정을 넣지 않은 모델 기본값, 끔 = `thinking: disabled`. effort = `output_config.effort`. 온도는 시험하지 않음.
- **think가 하는 일**: 답 전에 속으로 먼저 생각하는 단계(출력 토큰으로 과금). 글자를 옮겨 적는 일에는 효과가 작을 것이라는 가설(시험으로 확인).
- **OCR**: Tesseract(`kor+eng`, `--psm 6`). 긴 이미지는 2000px 조각(겹침 100)으로 읽고 겹친 줄은 한 번만 남김. **T는 칸을 못 나눠** 'Sonnet이 읽은 항목이 OCR 전문에 80% 이상 들어 있는지'로 비교. TA는 OCR 글자만 AI에 보내므로 이미지 입력 토큰이 없어 비용 절감 폭을 볼 수 있음.

**예측 방법(호출 전)**: AI 설정은 조각 크기로 입력 토큰을 어림(공식 문서 방식: 28×28px 한 칸 = 1토큰, 긴 변 2,576px·이미지당 4,784토큰 초과는 모델이 줄여서 읽음 — Claude 4.7 이상 기준. 첫 시험은 가로×세로÷750·1568px로 어림했음)+안내문 600토큰, 출력은 실측 Sonnet 평균 3,940토큰/건. TA는 OCR 글자 수÷1.5를 입력으로 어림. T는 0원.
**실제**: 응답이 알려 준 토큰으로 계산. 내용 차이는 기준선 항목마다 비슷한 글(유사도 0.8↑)을 찾았는지.

**준비·실행**: Tesseract가 컨테이너에 있어야 하므로 `Dockerfile`에 `tesseract-ocr tesseract-ocr-kor` 설치를 추가함(이미지 약 100MB 증가) → `--build` 필요.
```bash
sudo docker compose up -d --build api
nohup sudo docker compose exec -T api python -m scripts.image_compare --n 8 --out /tmp/image_compare.md > ~/image_compare.log 2>&1 &
# 일부만: --configs S,H1,G5,T,TA
```
