# 잡코리아 상세 수집과 검증

## 현재 경로

1. 검색 결과에서 공고 번호, 제목, 회사명, 경력·지역을 읽는다.
2. 새 공고의 상세 페이지를 열고 `iframe[srcdoc]` 안의 채용 본문만 추출한다. 바깥 페이지의 추천공고, 면접 후기, 복지 광고는 본문에 넣지 않는다.
3. 메타 설명의 마감일, 상세 페이지의 작성 회사명과 기업 정보(업종·규모·주소)를 확인한다.
4. 본문에서 담당 업무와 필수 요건을 분리하고, 명백히 관련 없는 직무와 마감 공고를 제외한다. 회사명이 일치하고 회사 업종까지 읽힌 공고만 DB에 저장한다. 우대 사항은 원문에 있을 때만 채운다.
5. 본문이 이미지이거나 별도 로딩되어 글자를 얻지 못하면 저장을 보류하고, 실행 기록에 사유별 건수를 남긴다.

2026-11-27 운영 서버에서 `로봇` 한 쪽(20건)을 시험했다. 신규 후보 9건 중 2건은 이미지, 7건은 업무·필수 구역을 확인하지 못해 저장 0건이었다. **이 결과는 잡코리아 수집이 완성되었다는 뜻이 아니다.** 이미지의 전체 글자 OCR과 항목 분류를 사용자 정답군으로 검증해야 이미지형을 자동 저장할 수 있다. 본문이 없는 텍스트형 화면은 별도 로딩 경로를 추가 조사해야 한다.

품질 검증에서 보류한 사람인·잡코리아 이미지 공고는 공고 DB 대신 `ocrCandidates`에 공고 URL과 이미지 URL을 기록한다. 이 목록은 제목·경력 필터를 통과해 상세 페이지까지 읽은 후보에 한정된다. OCR 실험은 PC에서 진행한다. 서버에서 실험 후보 목록을 꺼내는 명령:

```bash
cd ~/jobboard
sudo docker compose exec -T api python -m scripts.ocr_lab export-candidates --root /srv/files/ocr_lab
sudo docker compose cp api:/srv/files/ocr_lab/candidate_manifest.json /home/ubuntu/candidate_manifest.json
```

PC PowerShell에서 아래처럼 원본 URL 목록을 가져온 다음, PC의 OCR 실험 도구로 이미지를 내려받는다. 수집할 때 이미지 바이트와 SHA-256을 저장한다. 정답 전체 글자와 비교하기 전에는 이미지 공고를 자동 저장 대상으로 승격하지 않는다.

```powershell
scp -P 22 -i "$env:USERPROFILE\Downloads\ssh-key-2026-11-20.key" ubuntu@129.225.169.60:~/candidate_manifest.json .\candidate_manifest.json
python .\api\scripts\ocr_lab.py collect --manifest .\candidate_manifest.json --root .\ocr_lab_data
```

## 회사 정보 보강

자동 회사 보강은 접수 중이고 서버 판정이 `×`가 아닌 공고를 대상으로 사람인 기업 번호를 찾고, 회사 페이지의 항목별 정보를 저장한다. 잡코리아의 기존 공고 상세 재조회에서는 페이지 작성 회사명이 공고 회사명과 맞을 때 페이지의 업종·사원수·기업형태·주소도 빈 회사 칸에 저장한다. 같은 이름의 회사가 여럿이면 자동 확정하지 않는다. 개인별 `숨김` 목록은 계정별 기록에 동기화되지만 공고·회사 정보는 공용 데이터다. 한 계정에서 숨긴 공고가 다른 계정의 공용 회사 정보 보강을 중단시키지 않도록, 서버에서는 공용 `관련도 ×`와 마감 공고만 제외한다.

운영 DB 점검 당시 접수 중으로 분류된 1,470건 중 `회사 정보`가 비어 있는 공고는 1,424건이었다. 첫 보강에서 회사 번호 43곳을 찾고 회사 정보 50곳을 갱신해 공고 119건의 빈 회사 칸을 채웠다. 이후 예약 한도는 회사 조회 100곳·번호 검색 100곳/일이다. 사람인에 일치하는 회사 정보가 없거나 이름이 모호하면 빈칸으로 남는다. 이미 저장된 공고의 상세 본문·필수·우대는 신규 수집만으로 갱신되지 않으므로, `scripts.backfill_details`가 하루 최대 50건씩 재조회한다. 확인된 원문과 빈칸만 저장하며 이미지형·본문 별도 로딩형은 원인만 남긴다. 두 번 읽어도 실패하면 자동 재시도를 멈춘다.

2026-11-27 추가 보강에서는 회사 번호 75곳을 찾고 25곳은 모호해 보류했다. 회사 정보 70곳을 새로 저장하고 30곳을 갱신했으며, 공고 116건의 빈 회사 칸을 채웠다. 이후 접수 중·공용 관련도 `×`가 아닌 1,436건 중 회사 정보가 있는 공고는 289건, 아직 빈 공고는 1,147건이다.

같은 날 잡코리아 `로봇` 목록 1쪽을 다시 확인했을 때 신규 후보 9건 중 이미지 2건은 OCR 실험 후보로 저장했고, 7건은 업무·필수 구역을 분리할 수 없어 본 공고 DB에 넣지 않았다. 이미지 2건의 원본 파일은 PC OCR 실험 폴더에 SHA-256과 함께 저장했다. Haiku 제목 판정은 API 크레딧 부족으로 실패하여 9건 모두 `△`(판정 보류)로 처리됐다. 크레딧을 보충하기 전까지 자동 수집에서 Haiku 판정은 성공했다고 볼 수 없다.

첫 상세 재조회 20건에서는 5건의 업무·필수와 원문을 확인해 저장했고, 12건은 본문을 읽지 못했으며 3건은 구역 분리에 실패했다. 개인이 직접 쓴 필수·우대 값은 덮어쓰지 않았다.

같은 날 추가 재조회 50건은 모두 채용 본문을 읽지 못했다. 이 중 48건은 잡코리아 페이지 작성 회사명과 공고 회사명을 대조한 뒤 회사 정보(업종·사원수·기업형태·주소)를 공고별로 저장했다. 회사 정보가 채워진 것과 채용 본문을 읽은 것은 별개의 결과다.

## 다음 검증

- 대표 이미지의 원본과 사용자 정답 전체 글자를 저장하고 Haiku OCR 결과의 누락·오독을 비교한다.
- 이미지 OCR과 항목 분류를 따로 평가한다. 업무·필수·우대가 원문에 대응하는지 검증한 뒤에만 자동 저장을 허용한다.
- 잡코리아의 본문 별도 로딩 형식을 유형별로 수집한다. 못 읽은 유형은 조용히 빈 정보로 저장하지 않고 실행 기록에 남긴다.
- 기존 접수 중 공고는 신규 수집과 별도 백필에서 상세·회사 정보를 갱신한다. 기존 사용자 수정값을 덮지 않는다.
